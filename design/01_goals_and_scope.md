# 01. 学習ゴールと範囲

## 背景

- 元は Web エンジニア転職用のポートフォリオ（RAG チャットボット → 技術トレンドレーダー）。転職が決まり、その用途は終了。
- 転職先はスクレイピング・情報収集を本業とする会社。実務は TS / Node / Docker / K8s / BigQuery。
- このプロジェクトは仕切り直して、**フルスタック + インフラ運用の土台知識**を体系立てて身につける練習台にする。

## オーナーの現在地（自己申告）

- TypeScript: 読める。多少書ける。型の恩恵はまだ体感していない。
- HTML/CSS: セレクタは読める。書いた経験はほぼない。
- React: 未経験。
- バックエンド: ほぼ未知。
- DB: あやふや（SQL を書いた経験が浅い）。
- インフラ: Docker を触ったことはある程度。

→ **「動くものを下から組む」ことで、各層が何をしているかを手で理解する**のが狙い。

## ゴール（このプロジェクトで身につけたいもの）

1. **DB**: スキーマを設計し、migration で育て、シードを入れ、クエリを書ける。正規化・インデックス・トランザクション・N+1 を説明できる。
2. **API**: HTTP の上に型安全な API を組める。バリデーション・エラー設計・認証・ページングを実装できる。
3. **認証**: セッションと JWT の違い、Cookie 属性、パスワードハッシュ、認可（ロール）を実装レベルで理解する。
4. **フロント**: React の状態・副作用・レンダリングを理解し、API と繋いで画面を作れる。ルーティング・フォーム・データ取得の定番パターンを持つ。
5. **インフラ運用**: `docker compose` で全部が立ち上がる。migration を CI/CD で回す。ログ・ヘルスチェック・環境変数の扱いを知る。
6. **横断**: 型をフロント〜API で共有する旨み、モノレポの回し方、Conventional Commits、レビューの観点。

## 非ゴール（やらないこと）

- マルチテナント SaaS・RLS・BYOK など旧 TrendScope の重い要件は引き継がない。
- 本番デプロイ・独自ドメイン・課金は当面やらない（ローカル + CI が緑、が完了ライン）。
- 凝ったデザインシステム・アニメーション・デザイン性の作り込みはしない。
- 認証は「学習用に自前で薄く」組む。Auth0 / Supabase Auth などのマネージドは使わない（下の層を隠してしまうため）。
- スクレイピング機能そのものは作らない（実務で別途学ぶ）。題材は「よくある管理画面・業務アプリ」。

## 題材（何のアプリを作るか）

**社内向けの汎用管理コンソール**という体。ドメインは薄くていい。目的は「よくある画面・よくあるパターン」を作れる器を持つこと。

- 認証（ログイン / ログアウト / セッション維持）
- ダッシュボード（シェル + ウィジェット枠）
- 一覧・詳細・作成・編集・削除（CRUD の型）
- ユーザー / ロール管理（認可の型）
- 監査ログ・設定画面（読み取り主体の画面の型）

具体的なエンティティ（例: `users`, `items`, `audit_logs`）は [04_database.md](04_database.md) で決める。**最小限から始めて、画面を足すときにテーブルも足す**。

## 進め方

- **Sprint 1 で縦切りを 1 本通す**: `docker compose up` → DB migration 適用 → API 起動 → ログイン → ダッシュボードのシェル表示。ここまでを最優先。
- その後は [09_screen_catalog.md](09_screen_catalog.md) の台帳から画面を 1 つ選び、必要なら DB / API を足し、フロントを作る。これを繰り返す。
- 各作業は `design/sprint*/dayX.md` の指示書に沿って**オーナーが実装**。AI は設計・レビュー・詰まりの解消を担当。
- 1 タスク = 1 PR。Conventional Commits。CI（lint / typecheck / test）が緑でマージ。
