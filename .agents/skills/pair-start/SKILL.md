# pair-start — 切り分けたタスクを呼び出してペアプロを始める

このスキルは、`design/sprintN/dayX.md` に書かれた作業指示書から 1 タスクを選び、座布団さんと一緒に着手するセッションを開始する。**伴走モード固定**（1 手順ずつ確認しながら進める）。

## 進行プロトコル

### Step 1. タスク選択

座布団さんが**好きなタスクを選べる**ことを最優先する。デフォルトの「次の未完了」を押しつけない。

1. `design/sprint*/day*.md` を `Glob` で列挙し、すべてのタスク見出し（`## DayX-N.` 行）を抽出する。チェックリストの状態（完了/未完了/中断中）も併せて読む
2. ユーザーが既に明示している場合はスキップ
   - 「Day2-3 で」「Drizzle のスキーマを」などタスク特定済み → そのままそのタスクへ
3. 明示が無ければ `AskUserQuestion` で提示する。出し方は以下のルール:
   - **直近の未完了タスク 1 件**（推奨マーク付き）
   - **その日の他の未完了タスク**（同じ Day ファイル内で残っているもの全部、最大 2 件）
   - **「別の日を見たい」** 選択肢 — これを選んだら、もう一度 `AskUserQuestion` で Day を切り替えて再列挙
   - **「完了済みタスクを見直したい」** 選択肢 — レビューや手直し用
   - 各ラベルは `DayX-N. <タスク名>`、description は **目的 1 文** + **[自分]/[AI] タグ** + **(済) / (未) / (中断)** ステータス
4. 一覧が 4 件を超えるなら「別の日を見たい」経由でナビゲートさせる（`AskUserQuestion` は最大 4 options のため）
5. **どのタスクでも選べる**: 完了済みタスクが選ばれたら「これは完了済みです、見直し目的でいいですか？」と確認してから進む。順番を飛ばしても警告のみで阻止しない（前提確認は Step 4 で実機検証されるので、本当にブロックなら自然に止まる）

### Step 2. 位置づけと進め方の地図（オリエンテーション）

細部に入る前に、**「これは何の作業か」→「なぜ今これか」→「今日どう進むか」** を順に渡す。座布団さんは入門レベルなので、**まず "そもそも何をする処理で、出てくる用語は何者か" を新卒にも分かる言葉で噛み砕く**。ここを飛ばして前後関係や手順から入ると、用語が分からず迷子になる（実際に一度それで詰まった）。

材料を読む（Step 1 の day ファイルに加えて）:

- 該当 Sprint の `design/sprintN_plan.md` — **ゴール / 全体マップ（どの日が何を産むか）/ Sprint 全体ロードマップ（この Sprint が製品のどこか）**
- day ファイル冒頭の **テーマ・完了時の状態** と、前日の「次の日への引き継ぎメモ」
- **そのタスクが参照している `design/` ファイル**（各 day の冒頭「参照:」行と、前提確認・手順に出てくるもの）。用語と処理内容を正しく噛み砕くために読む
  - 層ごとの正: DB=`04_database.md` / API=`05_api.md` / 認証=`06_auth.md` / フロント=`07_frontend.md` / インフラ=`08_infra_ops.md` / 構成=`03_architecture.md`
  - **書き方の規約**は `docs/conventions/` が正（`typescript.md` / `react.md` / `sql.md`）

3 ブロックに分けて見せる（新卒に説明するつもりで。各ブロックは簡潔に、ただし**知らない言葉を 1 つも残さない**）:

1. **これは何をする処理か（ゼロ知識サマリ）** ← 最優先。ここが無いと残り 2 つは意味を成さない
   - まず 1〜2 文で「結局この作業は何をするのか」を、コードを書けない人でも絵が浮かぶ言葉で言う（例:「ログイン情報を保存する表の形を TypeScript で書いて、そこから DB に流す SQL を機械に作らせる」）
   - **タスク名・手順に出てくる固有名詞・略語・サービス名・データ形式を 1 つずつ展開する**（例: ORM とは / migration とは / Drizzle とは何をする道具か / `uuid` とは / `timestamptz` とは）。略語を略語のまま使わない
   - **使う技術スタックを言う**: 言語・実行環境・主要ライブラリ・保存先。**使わないもの**（例:「この回はまだ画面もサーバも無し、DB とスキーマだけ」）も言うと安心材料になる
   - **できあがるもの**: どのファイルに何が入るか
2. **このタスクの位置づけ（なぜ生まれ、何の役割か）**
   - Sprint のゴールは何で、このタスクがそこにどう効くか
   - **前段が残したもの → このタスクが使って作るもの → 後段が待っているもの** の鎖を 1 本で示す（例: Day 2 の `users` テーブル → 今日の `findUserByEmail` → Day 4 のログイン API）。これが「必要に応じて生まれた」の中身。最初のタスクなら「ここが起点」と言う
   - ロードマップ上の現在地（1 PR 粒度の 1 個）
3. **今日の進め方の地図**
   - 指示書の **手順** を着手順に 1 行ずつ並べる（ステップ数 + 各ステップ一言 + [自分]/[AI] の別）
   - 「この順で 1 つずつ伴走し、各ステップ後に動作確認を入れます」と進め方を宣言する

**渡してよい / 伏せるの線引き**: 処理の意味・用語・技術スタックは **全部渡す**（理解の土台）。伏せるのは **実装コードの中身だけ**（関数本体・具体的な書き方・核心のアルゴリズム）。「何をするか」を説明せず手順だけ見せるのは禁止。

ここは**説明だけ**。手は動かさない。タスクの目的・Done の詳細確認と着手 OK は次の Step 3 で取る。

### Step 3. タスクの確認

選ばれたタスクの該当節を `Read` で精読し、以下を 1 ターンで要約して座布団さんに見せる:

- **目的**（指示書から要約、1〜2 行）
- **自分で書く理由 or AI 依頼テンプレの要点**
- **完了時の状態**（Done の定義）

「この理解で進めて OK ですか？」とユーザーに確認する。NO なら指示書側を更新するか、別タスクへ切替。

### Step 3.5. 丸写しチェック（[自分] タスク必須）

着手前に、指示書の **手順** が **「答えのコードをそのままコピペするだけ」になっていないか** を確認する。完成コードがベタ貼りされていると、座布団さんは写経するだけになり、OJT の目的（自分で考えて書いて覚える）を外す。`[自分]` タスクでこれを検出したら、**着手させずに指示書を直す方へ倒す**。

判定の目安:

- **NG（丸写し）**: 手順にメソッド本体や SQL 全文が完成形で書かれている。読んで打つだけで考える余地がない
- **OK（伴走になる）**: 手順は「インターフェース・型・SQL の骨子・満たすべき条件」までで、実装本体は座布団さんが埋める前提になっている

NG なら座布団さんに「この手順は答えが書いてあるので、写すだけになります」と伝え、次のいずれかを提案する:

1. 手順を方針レベル（型・シグネチャ・満たす条件）まで落として、実装本体は伏せる
2. 大きく直すなら一度 pair-start を抜けて `sprint-plan` で指示書を修正する

`[AI]` タスクは委譲前提なので丸写しチェックの対象外（手順が具体的でも問題ない）。

### Step 4. 前提確認の実機チェック

指示書の **前提確認** チェックリストを、可能な限り実コマンドで検証する:

| 前提項目 | 検証コマンド例 |
|---|---|
| 前 day のチェックリストが揃っている | 指示書本文の Day(X-1) チェックリスト節を `Read` し、項目を列挙して聞く |
| 依存が入っている | `pnpm install --frozen-lockfile` |
| 内部パッケージが build 済み | `pnpm build`（`packages/*/dist` が無いと `@app/db` / `@app/shared` が解決できない） |
| 型が通る | `pnpm typecheck` |
| lint / format が通る | `pnpm lint && pnpm format:check` |
| postgres が起動している | `docker compose -f infra/compose.yaml ps`（`healthy` か） |
| api が動いている | `curl -s localhost:8787/health` |
| web が動いている | `curl -s localhost:5173/api/health`（Vite proxy 経由） |
| seed 済み | adminer（`localhost:8080`）で `users` に admin/member が居るか |
| `.env` の必要キーが揃う | `grep -E '^(DATABASE_URL\|SESSION_SECRET\|WEB_ORIGIN\|PORT)=' .env` |
| テストが green | `pnpm --filter @app/api test` / `--filter @app/web test` / `--filter @app/db test` |
| git ワーキングツリーが clean | `git status --porcelain` |
| 該当ファイルが既に存在しないか | `Glob` |

**Sprint 1 は下から積む**ので、Day が進むほど前提が増える（Day1=道具 → Day2=DB → Day3=API → Day4=認証 → Day5-7=フロント）。**その日に関係する行だけ**を実行する。全部流さない。

不足があれば、座布団さんに**何を埋めれば前提が揃うかを 1 つに絞って**伝える。複数欠けていたら最も大きな 1 個から。

### Step 4.5. 作業ブランチの用意

着手の前に **main 以外の作業ブランチに移る**（スキル自身の編集は例外的に main 直で良いが、**Day タスクのコードは main で直接書かない**）。手順:

1. 今いるブランチを確認（`git branch --show-current`）
2. **既存ブランチがあれば最優先で使う**:
   - 既に main 以外にいて、それが今回のタスクのブランチなら「このブランチで続けます」と伝えてそのまま使う
   - `git branch -a` に該当タスクのブランチ（`*dayX-N*` 等）があれば `git switch <名前>` で乗る
3. **無ければ新規に切る**: `git switch -c <type>/dayX-N-<slug>`（main 起点）
   - 形式は **`type/dayX-N-slug`**。`type` はタスク内容で選び（機能追加は `feat/`、整理は `chore/`・`refactor/`、ドキュメントは `docs/` 等。**AI が提案 → 本人確認**）、`slug` はタスク名の英語 kebab-case（例: `Drizzle のスキーマを入れる` → `feat/day2-3-drizzle-schema`）
   - `design/sprint1_plan.md` の「進めるときの 1 サイクル」に合わせる
   - 切る前に **Step 4 の clean 確認**を効かせる。無関係な未コミット変更を新ブランチに持ち込まない（別物なら先に commit/stash して切り分ける）
4. 用意したブランチ名を伝えてから Step 5 へ進む

### Step 5. 進行モード = 伴走

**伴走モードのルール**:

- 指示書の **手順** を 1 ステップずつ進める
- 1 ステップ実行ごとに「動きました？」相当の確認を入れる
- [自分] タスクは **コードを座布団さんが書く**。AI は雛形/質問への回答/レビューに徹する。先回りして `Write` してはいけない
- [自分] タスクでは、ユーザーが明示的に「答えを教えて」と解除するまで、**完成コード・そのまま穴埋めできるコード断片・正解の式・正解のメソッド呼び出しを出力しない**
- [自分] タスクへの返答は、原則としてコードブロックを使わず、**概念説明・入力と期待結果・確認質問・ユーザーが書いたコードのレビュー**に限定する
- 修正点を伝えるときは **対象項目と間違っている理由まで**に留め、正解の記述方法は示さない。必要なら段階的なヒントを 1 つだけ出し、ユーザーの次の実装を待つ
- 返答前に「この回答だけで正解コードを復元・コピペできないか」を確認する。できる場合は抽象度を上げてから返す
- [AI] タスクは指示書の **AI 依頼テンプレ** をそのまま実行する。委譲範囲を勝手に広げない
- 1 ステップが大きすぎると感じたら、その場でさらに分解して提案する
- ステップを終えるごとに「完了確認」の該当項目をその場で実機検証する
- 詰まったら、指示書の **詰まったら** 節を最初に参照する

### Step 6. セッション終了時

タスク完了 or 中断時に必ず:

1. 指示書の該当タスクの完了確認チェックボックスを `Edit` で `[ ]` → `[x]` に更新（実際に完了した項目のみ）
2. **未完了で中断した場合**は、Day ファイル末尾に「Day X 中断メモ」セクションを追加し、どこまで進んで何が残っているかを 3 行以内で記録
3. **Step 4.5 で用意した作業ブランチに commit**（conventional commits・メッセージは日本語可）。完了・中断どちらでも、その日の成果はブランチに残して push する（`git push -u origin <ブランチ>`）。**main へは直接 push しない**
4. **PR を出すかは本人判断**。出すなら `/pair-review` で差分をレビューしてから。push 後に「PR を出しますか？」と一度だけ聞く
5. memory（`MEMORY.md`）には書かない — タスク進捗は指示書側を正とする
6. 「次に進めるなら DayX-(N+1) です」「今日はここまでで切るのが良さそうです」のいずれかを提案

## やってはいけないこと

- **指示書にないタスクを勝手に始める** — 「ついでに」を禁じる。指示書 update が必要なら一度 pair-start を抜けて sprint-plan で修正
- **[自分] タスクで AI が先回りして `Write` する** — お手本を奪うのは禁止。座布団さんがコードを書く 1 行目を必ず待つ
- **[自分] タスクで正解コード・式・API 呼び出しを会話に直接書く** — ファイルを書かなくても答えを漏らせば同じ。ユーザーが明示的に解除した場合だけ許可
- **複数タスクを並列に走らせる** — Kitchen Sink Session 防止
- **「全部書きました、レビューしてください」モードに入る** — 伴走モード固定（ユーザーの合意済み）
- **進捗を `memory/` に書く** — 指示書のチェックボックスが唯一の正
- **着手前にスコープを膨らませる** — 「テストもついでに」「ドキュメントも」と言い出さない。指示書通り
- **丸写しになる [自分] タスクをそのまま着手させる** — 答えがベタ書きされた手順は写経。Step 3.5 で止める
- **用語を噛み砕かずに位置づけ・手順へ進む** — Step 2 は「これは何をする処理か」から。`HN`/`API`/`JSONL` のような語を未説明のまま使わない（新卒が迷子になる）
- **オリエンテーションで手を動かし始める / 脱線して講義になる** — 各ブロックは簡潔に。ただし知らない言葉は残さない
- **Day タスクのコードを main で直接書く / main に直接 commit する** — 必ず作業ブランチ（`type/dayX-N-slug`）を切ってから（Step 4.5）。スキル自身の編集だけは例外

## 落とし穴チェックリスト（毎セッション意識）

- [ ] 「これ Day X のタスクですか？」と確認したか
- [ ] **これは何をする処理か・出てくる用語・技術スタック**を新卒にも分かる言葉で説明したか（Step 2 ブロック 1）
- [ ] このタスクが**全体のどこで・なぜ今必要か**と**今日の手順の地図**を説明したか（Step 2 ブロック 2-3）
- [ ] [自分] タスクの手順が**丸写しになっていないか**確認したか（Step 3.5）
- [ ] 前提確認を**実行**したか（読むだけでなくコマンド実行）
- [ ] **作業ブランチを用意したか**（main で直接書いていないか・既存があれば使ったか）（Step 4.5）
- [ ] 1 ステップずつ進めているか（5 手順まとめて実行していないか）
- [ ] [自分] タスクで Write を先回りしていないか
- [ ] [自分] タスクへの返答に、コピペ可能な正解コード・式・メソッド呼び出しが含まれていないか
- [ ] 完了したチェックボックスを更新したか
