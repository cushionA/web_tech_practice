# sprint-plan — Sprint を作業指示書に分解する

このスキルは、本リポジトリのオーナー（駆け出し Web エンジニア、座布団さん）が AI とペアプロで進むための **作業指示書一式** を生成する。

## 入力

ユーザーから受け取る情報:

1. **Sprint 番号**（例: `Sprint 2`）
2. **Sprint ゴール**（自然文で OK）
3. **回数**（既定 3 回。Sprint 1 は 7 回だった）

不足していたら必ず `AskUserQuestion` で確認する。Sprint ゴールが曖昧なら `design/sprint1_plan.md` の「Sprint 1 完了後に残るタスク」と `design/09_screen_catalog.md` の候補表を読んで提示する。

> **「日」ではなく「回」で数える**（`design/README.md` の進め方の原則）。ファイル名は `dayX.md` のままだが、カレンダーの 1 日とは対応しない。1 回 2〜4 時間、詰まったら 1 回を 2 回に割ってよい。見積は伸びる前提で書く。

## 前提として読むファイル

実行開始時に必ず以下を確認する（既に読み込まれていなければ Read する）:

- `design/README.md` — ドキュメント一覧と進め方の原則
- `design/10_conventions_pointer.md` — **[自分] / [AI] 委譲方針と層ラベルの正**
- `design/01_goals_and_scope.md` — ゴール / 非ゴール / オーナーの現在地（スキル前提）
- `design/sprint1_plan.md` および `design/sprint1/day1.md`〜`day7.md` — フォーマットの参照実装
- 該当 Sprint の中心になる設計書（層ごとの正: `03_architecture` / `04_database` / `05_api` / `06_auth` / `07_frontend` / `08_infra_ops` / `09_screen_catalog` / `11_bot_detection`）

これらが食い違ったら **`design/` を信じる**（ルート `CLAUDE.md` の方針）。書き方の規約は `docs/conventions/` が正。

## 委譲ルール（[自分] vs [AI]）

`design/10_conventions_pointer.md` の「委譲方針」を機械的に適用する。基準:

> 「面接で『これどうやって作った？』と聞かれて、その場で説明できる必要があるか」
> - YES → [自分]
> - NO → [AI]

**このプロジェクトは学習が目的**なので、既定は [自分] に強く倒れる（`design/README.md`: 器・練習場・追加画面の実装コードはオーナー本人が書く）。

| 種別 | 委譲先 |
|---|---|
| スキーマ設計 / API インターフェース / 認証ロジック / 型定義の骨子 | **[自分]** |
| 画面・コンポーネント・hooks・ルーティング・フォームの実装 | **[自分]**（React を手で覚えるのが目的） |
| migration SQL / Dockerfile / compose / CI YAML の一次案 | **[自分]** が書く。詰まったら [AI] が雛形提示 |
| 定型の複製（2 個目以降の似た CRUD 画面・テストの横展開） | [AI]（**1 個目を自分で作った後**） |
| 設計ドキュメント / Day 指示書 / レビュー / 詰まりの解消 | [AI] |
| 「最初の 1 個」 | **[自分]**（残りは [AI] で複製可能になる） |

判断に迷ったら **[自分] に倒す**。座布団さんが後で「これ説明できないな」となるのが最悪。

## 層ラベル（フルスタックの守備範囲を可視化）

委譲タグ（[自分]/[AI]）に加えて、各タスクに **層ラベル** を併記する。フルスタックのどの層を踏んでいるかを可視化し、偏り（特に放置しがちな `[INFRA]`）を見えるようにする。凡例の正は [`10_conventions_pointer.md`](../../../design/10_conventions_pointer.md) に置く。

| ラベル | 範囲 |
|---|---|
| `[FE]` | フロントエンド: 画面/コンポーネント/hooks/フォーム/ルーティング・レイアウト/画面レジストリ |
| `[BE]` | バックエンド: API ルータ/ミドルウェア/認証・認可/クエリ関数/サーバ側バリデーション |
| `[INFRA]` | インフラ: Docker / compose / CI・CD / migration 運用 / 環境変数・シークレット / 依存更新 |
| `[TEST]` | テスト: 単体/結合/E2E/Testcontainers/認可マトリクス/seed |
| `[設計]` | 上流設計: スキーマ設計/インターフェース定義/仕様明文化（コード実装を伴わない設計タスク） |

- 委譲タグの **後ろ** に付ける: `## Day2-3. packages/db に Drizzle とスキーマを入れる [自分] [BE] [設計]`
- 複数層にまたがるタスクは主たる層を先頭に併記（最大 2、稀に 3）。例: CRUD 画面 = `[FE] [BE]`、compose + スキーマ = `[INFRA] [BE]`。
- migration の**運用**は `[INFRA]`、スキーマの**設計**は `[BE] [設計]`。認証ロジックは `[BE]`。
- 各回に層の偏りがないか軽く確認し、`[INFRA]` や `[TEST]` がゼロの回が続かないようにする。
- **`[ML]` は使わない**（このプロジェクトに ML は無い。旧 TrendScope の名残）。

## 出力ファイル

### `design/sprintN_plan.md`（Sprint 全体マップ）

含めるセクション:

1. テーマ・期間・ゴール・完了時の状態
2. 全体マップテーブル（| 日 | テーマ | 詳細指示書へのリンク | 主成果物 |）
3. 各 day の概要（タスクリストのみ、詳細は day ファイルに譲る）
4. 進めるときの 1 サイクル（`design/sprint1_plan.md` の「進めるときの 1 サイクル」に合わせる）
5. 「つまづいたらここを見る」表（症状 → 参照先）
6. Sprint 完了後に残るタスク

### `design/sprintN/dayX.md`（日次作業指示書）×日数

各 day ファイルの構成:

```
# Sprint N Day X 作業指示書

> テーマ: ...
> 完了時の状態: ...（実際に叩けるコマンド / 見える画面で書く）
> 推定所要: X〜Y 時間
> 主に踏む層: `[BE]` `[TEST]`

参照: [design/0X_....md](../0X_....md)（何の正か）/ [docs/conventions/xxx.md](../../docs/conventions/xxx.md)

---

## DayX-1. <タスク名> [自分] or [AI] [層ラベル]

**目的**
何のために、面接で何を語れるか（1-2 段落）

**自分で書く理由** (←[自分] の場合のみ)
なぜ AI 委譲せず自分が書くか

**前提確認**
- [ ] チェック項目
- [ ] チェック項目

**手順**
1. ...（**ヒント**: シグネチャ・型・満たすべき条件まで。**実装本体は書かない**）
2. ...

**完了確認**
- [ ] 検証コマンド or 動作確認
- [ ] テスト green

**詰まったら**
- 症状 → 対処

**AI 依頼テンプレ** (←[AI] の場合のみ)
\`\`\`
依頼文をそのままコピペできる形で
\`\`\`

---

(タスクを 3-6 個繰り返す)

## Day X 終了チェックリスト
- [ ] ...

## Day X+1 への引き継ぎメモ
- ...
```

## 分解の粒度ルール

- 1 タスク = 1 PR の単位
- 1 回あたり 3〜6 タスク、合計 2〜4 時間を目安
- 最初の 1 タスクは前回からの「前提確認」にする（リハビリ。**成果物が無いので PR にはしない**と明記する）
- 各回に最低 1 つは [自分] のタスクを入れる（実際にはほぼ全部が [自分] になる）
- 同じテーマを複数タスクで分割するときは「最初の 1 個（[自分]）」→「残り複製（[AI]）」のパターンに寄せる
- **未経験の層は薄く割る**。オーナーは React 未経験・BE ほぼ未知（`01_goals_and_scope.md`）。Sprint 1 でフロントを 1 回に詰めて破綻し、3 回（Day 5-7）に割り直した前例がある。**新しい概念が 3 つ以上出る回は割る**
- 新しいライブラリを初めて使う回は、その前に**素振り**（`notes/*_basics.md`）を置けないか検討する

## 完了後にすること

1. `design/README.md` の「Sprint」表に新規 Sprint プランを追記
2. 生成した day1.md のパスをユーザーに伝え、「次はこれを開いて Day1-1 から」と案内
3. **書き終わった作業指示書を git に commit しない**（ユーザーが内容を確認・修正してからコミットしたい）
4. リンク切れが無いか確認する（`design/` 内の相対リンクと `docs/conventions/` への `../../` パス）

## やってはいけないこと

- 設計書（`design/`）を勝手に書き換える — 食い違いを発見しても、まず指摘してユーザー判断を仰ぐ
- Sprint N の途中で別 Sprint の話を混ぜる（Kitchen Sink Session 防止）
- 「念のため」セクションを足して指示書を肥大化させる — 読まれない章を作らない
- [自分] タスクの手順を AI 委譲できる粒度に逃がす — 自分で書く部分は「インターフェース・型・SQL の骨子」までを必ず含める
- **[自分] タスクの手順に完成コードを書く** — 写経になる。ヒント（シグネチャ・型・条件）で止める。`pair-start` の Step 3.5 で弾かれる粒度を最初から作らない
- **設計書にバージョン番号を書く** — 実バージョンの正は `package.json` + lockfile（`02_tech_stack.md` のバージョン方針）
- **`[ML]` ラベルを使う** — 旧 TrendScope の名残。このプロジェクトには無い
